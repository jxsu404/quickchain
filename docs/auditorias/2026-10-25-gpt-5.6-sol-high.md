# Auditoría independiente de QuickChain

**Fecha de corte:** 2026-10-25, 11:31 p. m. CR  
**Alcance:** `docs/PLAN-OPUS.md`, documentación, contrato Soroban, `agent-client`, `api-demo`, `web`, scripts, CI y artefactos de despliegue.  
**Criterio:** el código y los artefactos ejecutables prevalecen sobre las declaraciones de los documentos.

## Veredicto ejecutivo

QuickChain ya tiene un núcleo técnico demostrable: cuenta-contrato con `__check_auth`, SDK x402, vendedor, facilitador, comisión y evidencia de pagos en testnet. No encontré una vía para que la llave del agente sobrepase el **tope total on-chain** mediante el token configurado.

La entrega todavía no demuestra el producto prometido de punta a punta. La web solo hace login; no despliega una cuenta, no crea trustline, no firma `renovar` y no muestra estado. Tampoco hay una corrida única y limpia que una Cavos → presupuesto → SDK → API x402 → bloqueo → comisión. El mayor riesgo para el deadline no es el contrato: es la integración y la evidencia final.

Estado de Q0–Q15 basado en implementación: **4 hechas, 7 a medias y 5 sin empezar**.

### Escala de severidad

- **Crítica:** pérdida fuera del tope o compromiso directo de llaves/fondos.
- **Alta:** permite consumir fondos o fees de forma no autorizada dentro de límites relevantes, o rompe un control de seguridad principal.
- **Media:** debilita una garantía, permite cobros duplicados o causa bloqueo/pérdida operativa recuperable.
- **Baja:** robustez, configuración o discrepancia con la promesa sin explotación directa importante.

No identifiqué un hallazgo crítico en el contrato. Sí hay dos riesgos altos en el perímetro SDK/facilitador.

## 3. Huecos entre plan y código

1. **La diferenciación principal no está implementada.** Contrato, SDK y API funcionan; correo + una firma mensual + panel no. Hoy la demo real es principalmente CLI.
2. **El plan parte de una premisa ya refutada por la propia evidencia.** `PLAN-OPUS.md:8` afirma que el facilitador público rechaza `C…`; `docs/transacciones.md:13-18` registra cuatro pagos de `C…` con el facilitador público. Mantener uno propio agrega S-02 sin necesidad para la demo.
3. **El plan referencia código inexistente.** `PLAN-OPUS.md:31` y `196` dicen que existe `web/src/billetera/` y un fallback Freighter; no hay tal carpeta ni dependencia.
4. **La primera alta no puede prometer una sola firma total.** Trustline y fondeo son preparación adicional. La promesa defendible es “una firma por renovación mensual después del onboarding”.
5. **No hay “mes calendario” en contrato.** Solo hay un timestamp elegido por el dueño y renovaciones anticipadas posibles.
6. **`max_por_llamada` no limita el agregado de una autorización.** El código y su test aceptan varias transferencias.
7. **La comisión de 1 % puede quedar como deuda no respaldada.** La demo funciona si se carga al menos el tope, pero el contrato no exige ese invariante.
8. **La seguridad descrita excede la implementada.** No hay rate limit del SDK, allowlist segura frente a redirects ni política de acceso del facilitador.
9. **No hay despliegue Vercel verificable en el repo.** Tampoco configuración/URL que pruebe los dos proyectos Next.js.
10. **Documentación operativa contradictoria.** `ARQUITECTURA`, `PLAN`, `TAREAS`, `SEGURIDAD`, `README`, `web/AGENTS.md` y `DEMO` mezclan el diseño viejo con el actual.
11. **La evidencia está fragmentada.** Los hashes son valiosos, pero no demuestran una sesión de usuario completa ni la integración Cavos.
12. **La entrega no está preparada.** Pitch, slides, video, validación y APEX siguen incompletos.
13. **CI no prueba el SDK ni construye las apps Next.** Puede quedar verde con un flujo x402 roto en runtime o con un fallo de `next build`.
